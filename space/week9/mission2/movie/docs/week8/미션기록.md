# 8주차 서버 필수 미션 — 즐겨찾기와 영화 기록

## 구현 결과

Spring Boot 스택으로 `C:\Coding\UMC2\space\week8\mission2\movie`에 구현했다. 앞선 작업에서 만든 즐겨찾기를 재사용하고 영화 기록 저장 API를 추가했다.

| Method | URL | 결과 |
| --- | --- | --- |
| POST | /favorites | 201, 즐겨찾기 저장 |
| GET | /favorites | 200, 내 목록 최신 등록 순 |
| GET | /favorites/{movieId} | 200, isFavorite 여부 |
| DELETE | /favorites/{movieId} | 200, result: null |
| POST | /movie-records | 201, rating과 favorite 반환 |

모든 API는 인증이 필요하다. 요청 URL·쿼리·본문으로 회원 ID를 받지 않고, AuthInterceptor가 검증한 토큰의 회원 ID를 사용한다. movieId는 TMDB 식별자이며 우리 DB의 영화 외래 키가 아니다.

## 진행 과정

1. 새 워크북의 Spring 예제와 기존 코드를 비교했다. Favorite 엔티티·Repository·Service·Controller와 복합 UNIQUE 제약은 이미 구현되어 있었다.
2. CreateMovieRecordRequest와 MovieRecordResponse를 추가했다. 영화 ID는 양수, 별점은 1~5, addToFavorites는 필수 Boolean이다. comment는 워크북 영화 기록 명세에 따라 선택이며 별도의 500자 검증을 추가하지 않았다.
3. MovieRecordService에서 회원 존재, 평점 중복, 선택한 경우 즐겨찾기 중복을 검사했다. 예외 코드는 MEMBER404_1, RATING409_1, FAVORITE409_1을 사용했다.
4. Service의 public create 메서드에 @Transactional을 적용하고 두 Repository 저장을 같은 메서드에서 실행했다. Controller가 Spring 프록시를 거쳐 호출하므로 동일 클래스 내부 호출 문제를 피했다.
5. addToFavorites가 false이면 평점만 저장하고 favorite은 null로 반환한다. true이면 두 저장이 모두 성공해야 commit된다.
6. MockMvc와 H2로 실제 Controller·Service·DB 흐름을 테스트했다. 응답 JSON은 테스트 실행 결과를 그대로 파일로 저장했다.
7. 단순 중복 사전 검사는 rollback 증명이 아니므로, 평점을 flush한 뒤 두 번째 저장에서 예외가 발생하는 테스트를 추가했다. 트랜잭션 종료 후 평점이 남지 않는 것을 확인했다.

## 핵심 코드

[MovieRecordService 코드](MovieRecordService.java)

```java
@Transactional
public MovieRecordResponse create(Long memberId, CreateMovieRecordRequest request) {
    // 회원 존재와 중복 검사 후 실행
    var rating = ratings.saveAndFlush(Rating.builder()
            .member(member).movieId(request.movieId())
            .score(request.score()).comment(request.comment()).build());
    FavoriteResponse favorite = null;
    if (request.addToFavorites()) {
        favorite = FavoriteResponse.from(
                favorites.saveAndFlush(new Favorite(member, request.movieId())));
    }
    return new MovieRecordResponse(RatingResponse.from(rating), favorite);
}
```

위 코드는 저장 부분을 발췌한 것이다. 전체 회원 조회·중복 검사 코드는 첨부한 소스에 있다.

**두 저장을 묶은 이유:** 평점 또는 즐겨찾기 저장 중 하나라도 실패했을 때 다른 저장도 취소하여 사용자 요청이 일부만 반영되지 않도록 하기 위해서다.

## 문제와 해결

**문제:** 중복을 사전에 거절하는 테스트만으로는 첫 번째 저장 후 두 번째 저장 실패 시 rollback되는지 알 수 없다.

**해결:** 테스트 전용 Repository spy로 두 번째 저장에서 예외를 발생시켰다. 예외 발생 직전에 첫 번째 평점이 DB에서 조회됨을 확인하고, 서비스 예외 전파 후에는 평점이 없어졌음을 확인했다. 운영 코드에 강제 실패용 로직은 넣지 않았다.

## 핵심 키워드

- **트랜잭션:** 여러 DB 작업을 하나의 작업 단위로 묶는 것.
- **commit / rollback:** 변경을 최종 확정하는 것 / 해당 트랜잭션의 변경을 취소하는 것.
- **원자성:** 묶인 작업이 모두 성공하거나 모두 취소되는 성질.
- **ACID:** 원자성, 일관성, 격리성, 지속성. 트랜잭션의 부분 저장을 막고, 제약을 지키며, 동시 실행의 영향을 제어하고, 확정한 결과를 보존한다.
- **UNIQUE:** 지정한 컬럼 조합의 중복 저장을 DB가 막는 제약. 여기서는 회원과 영화 ID의 조합이다.
- **낙관적 잠금:** 버전 값 등을 비교해 다른 요청이 먼저 수정했는지 확인하고 충돌을 감지하는 방식. 이번 미션에는 적용하지 않았으며 UNIQUE 제약과는 역할이 다르다.

## 학습 후기 질문

1. **평점만 저장되면 왜 문제인가?** 사용자는 평점과 즐겨찾기를 함께 요청했는데 결과가 일부만 반영된다. 재요청 때 중복 오류가 생겨 복구하기도 어려워진다.
2. **서버 중복 검사와 UNIQUE가 모두 필요한 이유는?** 사전 검사는 이해하기 쉬운 오류를 제공하지만 동시 요청이 모두 통과할 수 있다. DB UNIQUE가 최종 중복 저장을 막는다.

선택 미션인 Swagger UI 적용, Notion 게시, UMC 제출은 이번 필수 미션 범위에 포함하지 않았다.
